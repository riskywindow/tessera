## 0. Environment corrections found during recon

The mission brief's section 4 assumptions were checked first. Four were wrong. The corrected table is in `CLAUDE.md` §4 and summarized here:

1. **The local host is x86-64 Ubuntu 26.04**, not arm64 Ubuntu 24.04. arm64 coverage therefore comes from cross-compiling (gcc-15 and clang-20) and running the CPU tests under `qemu-aarch64`. A CI workflow for native `ubuntu-24.04-arm` also exists but cannot run until a git remote exists (question for HC-0).
2. **The local root filesystem is 100% full.** Root has about 4 GiB of reserved blocks. The human's other projects use the rest, and none of them are touched. Build trees go on tmpfs (`/tmp/tessera-build`), and apt archives were downloaded to tmpfs.
3. **`cuda.h` is in `cuda-cudart-dev-12-6`**, not `cuda-driver-dev-12-6`. The latter holds only `stubs/libcuda.so`, which we use as the authoritative export list for forwarding (640 symbols in 12.6.77).
4. Toolchains available locally: gcc 15.2, clang 20.1.8, clang-tidy 20, clang-format 19.1.7, CMake 3.31.6, Ninja 1.13.2. The brief's minimum versions (clang 18, gcc 13) are exercised in the Modal image, which is jammy-based.

**WP-0.2.**

**WP-0.3.**
- `scripts/check_all.sh` exits 0 and prints a per-configuration summary. The configurations are:
  - native x86-64: gcc-debug, gcc-release, clang-debug, clang-release, gcc-asan (ASan+UBSan), clang-asan (ASan+UBSan), clang-tsan;

**WP-0.4.** A GoogleTest suite for the fake itself covers:
- stream FIFO ordering and simulated-time kernel durations;
- event record/query/elapsed;
- stream and context sync;
- memory alloc/free and memcpy;
- `cuGetProcAddress`/`_v2` resolution by `(symbol, cudaVersion, flags)` to the correct versioned or `_ptsz` variant;
- per-symbol invocation counters readable through a control API.

It is green under ASan/UBSan and TSan.

**WP-0.5.** CPU tests against the fake cover:

- **T1 interception matrix.** Covers 2 strategies:
  - masquerade: the shim is `libcuda.so.1` on `LD_LIBRARY_PATH`, with the real driver from `TESSERA_REAL_LIBCUDA`;
  - preload: `LD_PRELOAD=libtessera.so` plus a `dlsym` hook.

  Each strategy is tested over 4 access paths:
  - direct link (`DT_NEEDED libcuda.so.1`);
  - `dlopen("libcuda.so.1")` then `dlsym(handle, …)`;
  - `cuGetProcAddress` (v1);
  - `cuGetProcAddress_v2`, including looking up `cuGetProcAddress` itself, as cudart does.

  For every hooked symbol, three counts must be equal: calls issued by the app, the shim's per-symbol counter, and the fake's per-symbol counter.
- **T2 per-thread default stream.**
  - `cuGetProcAddress(…, CU_GET_PROC_ADDRESS_PER_THREAD_DEFAULT_STREAM)` for each stream-taking hooked symbol returns a shim wrapper whose call reaches the fake's `_ptsz` variant.
  - `LEGACY_STREAM` reaches the legacy variant.
  - Versioned names resolve by `cudaVersion`: for example, `cuMemAlloc` at 3000 goes to v1 and at 12060 goes to `_v2`.
- **T3 fork.**
  - Another parent thread holds a shim-internal lock at `fork()`. The child still completes a hooked call within 2 s.
  - The child's counters start at 0, and the parent's are unchanged.
- **T4 forwarding.**
  - Non-hooked symbols reach the fake unchanged through all 4 access paths.
  - Return codes and out-parameters pass through bitwise.
- **T5 lazy init.** Loading the shim triggers zero calls into the fake until the app's first driver call.
- **T6 misconfiguration.** `TESSERA_REAL_LIBCUDA` pointing at the shim itself returns an error and does not recurse.
- **T7 I-4 preliminary.** v0 adds launch counting to the hot path, so:
  - steady-state launches under the shim make 0 heap allocations (allocation-hook count);
  - steady-state launches make 0 syscalls (strace window count, native x86-64 only).

**WP-0.6.** `modal run infra/modal_gpu.py::m0_gate` builds the image and runs on L4:
- the CPU test suite in-image (clang-18 and g++-13);

## 2. Gate criteria (all hard)

The expected launch count for G9 is fixed here, before any shimmed run:
- **GEMM loop:** N iterations of `torch.mm(a, b, out=c)` with fixed shapes. The expected count is the number of kernel launches CUPTI records over the same window, via `torch.profiler` activity CUDA. This is a separate pass with the same inputs, because cuBLAS may issue more than one kernel per GEMM.
- **Elementwise control:** N iterations of `x.add_(1.0)`. The expected count is exactly N.
- **Pass condition:** the shim's counter delta over the window equals the expected count exactly for both loops.

**Pre-registered numbers.** The no-shim baseline has now been measured on an
L4 (`results/m0/gpu_baseline.json`), so the targets are written down here
before the shim is run against them, at N = 200:

| Loop | CUPTI device kernels | CUPTI host launch calls | Expected shim `launches` delta |
|---|---|---|---|
| GEMM | 400 | 200 runtime + 200 driver | **400** |
| control | 200 | 200 runtime + 0 driver | **200** |

The GEMM loop issues two device kernels per iteration, and the two are reached
by *different host paths* — one through the runtime API and one through the
driver API. That split is itself the point of the test: a shim that hooks only
one path lands on 200 and fails. `cupti_graph_launches` is 0 in both loops, so
the shim's `graph_launches` counter must also be 0 or the comparison is void.
G8's baseline hashes are recorded in the same artifact.

## 4. Risks

Risks found in M0 are tracked in `docs/RISKS.md`. The ones that affect this gate:
- the disk-full host;
- no native arm64;
- newer cudart (from PyTorch wheels) requesting driver symbol versions the 12.6 header does not know;
- the `dlsym(RTLD_NEXT)` caller-relative semantics in the preload strategy;
- ASan runtime ordering with `LD_PRELOAD`;
- MPS availability in Modal.
